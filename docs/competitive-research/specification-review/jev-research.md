# Jev の調査

調査日: 2026-09-20

## 調査の範囲

TypeSafe AIの[公式発表][announcement]と[公式スキル][official]を確認した。仕様書とコードの照合にJevを使う方法を調べ、今回の要件に照らして通常のLLMによる評価と比較した。APIの実行や、精度・速度・費用の比較測定は行っていない。

## 比較

今回の要件では、要求・設計・実装の対応を評価し、指摘の根拠や修正方針を確認できることを重視する。この用途に通常のLLMとJevがどう役立つかを、機能と運用の面から比較した。同じデータを使った性能測定は行っていない。

| 比較軸 | Jevの特徴 | 今回の要件での判断 |
| --- | --- | --- |
| 費用 | 公式資料では、判定にかかる費用の低さを利点としている | 今回も利点になり得る。通常のLLMによる評価と比べ、実際にどれだけ費用を減らせるかは未測定 |
| 応答速度 | 互いに独立した多数の質問に並列で回答し、高速に応答する設計になっている | 今回は即時の応答を求めていないため、導入の決め手にはならない |
| プログラムへの組み込み | 型付きの選択肢・確率・段階評価をコードで扱える | 今回は判定結果をプログラムの分岐に直接使うことが主目的ではないため、この利点の重要度は低い |
| 評価内容 | 判断結果を返すが、根拠や修正案を文章で生成しない | 根拠や修正方針まで扱う評価には通常のLLMを使える。Jevを併用するなら、判定結果をもとに説明を作る処理が必要 |
| 精度と運用全体の費用 | 対象データに合わせた質問・評価基準の設計と検証が必要 | 同等の評価品質を保てるか、連携や追加レビューを含めても安くなるかは未確認 |

Jevの特徴は[公式発表][announcement]と[公式スキル][official]に基づく。「今回の要件での判断」は、今回の使い方に合うかどうかを評価したものである。性能や費用の実測結果ではない。通常のLLMを比較対象とする場合も、モデルと評価手順を揃えて確認する必要がある。

## 分かったこと

1. **判断と実行を分けて組み合わせる。** `noul` は条件が成立する確率、`choice` は定義した選択肢からの選択、`score` は説明した段階に沿う評価を返す。既知の規則、計算、実行制御はコードが担当する。互いに独立した質問は、同じ情報を使って一度に評価できる。他の質問への回答が必要な場合は、その回答を得てから次の処理に進む。[公式スキル][official]
2. **判断に必要な根拠は呼び出し側が揃える。** 一つの質問では一つのまとまった判断を扱い、必要な条件や情報を渡す。仕様の照合に使う場合は、要件ID・受入条件を対象コードと対応付ける。要件書の作成に加え、Jevによる検査の仕組みも用意する必要がある。[公式スキル][official]、[受入条件とトレーサビリティ](../../../skills/create-requirements-docs/assets/requirements-template/10-acceptance-and-traceability.md)
3. **数値化は正しさの証明ではない。** 公式スキルも、型付き出力が保証するのは出力の形式であり、判断の正しさではないと説明している。判定の境界となるしきい値は、対象データと誤判定の影響を踏まえて、妥当かどうかを確かめる必要がある。公式発表の速度や効率に関する主張も、このリポジトリでの実測結果とは区別する。[公式スキル][official]、[公式発表][announcement]
4. **Jevは判断の理由を文章で説明しない。**結果が不確かな場合や不一致が疑われる場合は、根拠となる資料とともに人や推論モデルへ引き継ぐ方法が参考になる。問題の原因は、入力の不足、モデルの判断ミス、呼び出し側の実装不備、サービスの障害に分けて確認する必要がある。[公式スキル][official]

## このリポジトリへの適用案

今回の要件でJevに期待できる主な利点は、**評価コストの削減**である。応答の速さと型付きの出力も特徴だが、今回の用途では選定の決め手にはならない。Jevの導入はいったん見送る。

今回必要なのは、要求・設計・実装の対応を確認し、問題があれば根拠と修正方針を示す評価である。即時の応答や、判定結果に応じてプログラムの処理を自動で分岐させることは主目的ではない。そのため、現時点では通常のLLMによる評価を基本とする。

Jevで判定し、その結果を通常のLLMで説明する使い方も考えられる。ただし、判定の品質を保ちながら、連携の実装・運用や追加レビューを含めた費用まで減らせるかは未確認である。費用がどれだけ減るかを測らずに、導入の効果があるとは判断しない。

評価手順の整備は、通常のLLMを使用する前提で進める。調査から参考にするのは、要件・対象コード・評価観点を対応付け、入力不足と判断の誤りを分ける方法である。これらはJevの導入を前提としない。

この結論は、現時点の要件と公式資料を照らし合わせた判断である。実測比較でJevの性能が劣ると確認したものではない。評価の実施回数や費用が増えた場合、または即時の応答や型付き出力のプログラムへの組み込みが必要になった場合に、通常のLLMだけを使う方法と、Jevを併用する方法を改めて比較する。

項目別の判断は[採否検討](inclusion-review/jev.md)にまとめた。API利用、比較実験、CIへの導入、既存スキルへの反映は行っていない。
