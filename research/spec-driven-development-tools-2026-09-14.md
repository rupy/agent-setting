# 仕様駆動開発ツール調査

**1. 結論**

仕様駆動開発を支える58件を、AI向けの仕様・実装支援32件と、API契約、受入テスト、状態モデル、要件管理の周辺ツール26件に分類した。これらは同じ仕事をする58個の代替製品ではない。仕様を書く、変更を管理する、実装を進める、実装との一致を検証する、という異なる役割を担う。

要件定義・設計テンプレートの拡充を目的とする場合、最初に比較する価値が高いのは **GitHub Spec Kit、OpenSpec、Kiro、cc-sdd、BMad Method** である。機能仕様、変更差分、要件の記述方式、既存実装とのギャップ、事業要求から実装仕様への段階化をそれぞれ学べる。作業分割・継続実行まで範囲を広げるなら、Spec Kitty、GSD、Superpowersを追加する。この優先順位は機能の適合性に基づく分析であり、実測した性能ランキングではない。[^1][^2][^3][^4][^5][^6][^7][^8]

重要なのは、有名なツールのディレクトリ構成をそのまま採用することではない。テンプレート拡充では、既存の要件定義・基本設計・詳細設計を維持しつつ、機能・変更単位の仕様、例外条件、影響分析、検証証跡など不足しやすい成果物を補う方が目的に合う。

**2. 対象範囲と確からしさ**

情報の確認基準日は2026年9月14日。公式ドキュメント、公式リポジトリ、公開テンプレート、変更履歴を根拠とする。カタログには専用製品だけでなく、CLI、MCPサーバー、Agent Skills、仕様言語、テスト・要求管理ツールを含めた。単なる汎用AIエディタは、独立した仕様ワークフローを確認できる場合を除いて対象外とした。

本資料は公開資料に基づく比較であり、インストール、同一課題による実行試験、セキュリティ監査は実施していない。生成品質、トークン消費、速度、長期運用の安定性は評価していない。公式が述べる機能と、実案件での有効性は別である。網羅性を広く取った候補集であって、存在する全ツールを列挙できたという主張ではない。

特に小規模プロジェクトではREADMEが実装に先行する可能性がある。SpecPulseは存在と目的の確認にとどめ、詳細挙動は追加検証対象とした。公開リポジトリがあることは、任意用途で無条件に使えることを意味しない。採用やテンプレート転載時には対象版のライセンスと利用条件を別途確認する。[^31]

**3. 「仕様駆動」の五つの意味**

| 分類 | 主な入力 | 主な出力・役割 | 件数 |
|---|---|---|---:|
| AI仕様・実装 | 自然言語の要求、既存コード、プロジェクト規約 | 仕様・設計・タスク・実装支援 | 32 |
| API契約・生成・検証 | OpenAPI、AsyncAPI、Protobuf等 | コード生成、モック、互換性・契約検査 | 11 |
| 実行可能な受入仕様 | 振る舞いの具体例・シナリオ | 実行する受入テスト | 5 |
| 形式仕様・状態モデル | 状態、遷移、関係、論理条件 | モデル検査、静的検証、状態機械の実行 | 4 |
| 要件管理・トレーサビリティ | 要求ID、属性、関係、レビュー | 変更管理、追跡、証跡 | 6 |

この分類は本資料の分析上の整理であり、各製品が採用する公式分類ではない。例えばTask MasterやAPMはAI仕様・実装に含めたが、中心はタスクや文脈の管理である。Tesslは旧来のSDD文脈との関係から収録したが、現行の主用途には大きな変更がある。[^19][^20][^14][^61]

自然言語をエージェントに読ませる方式と、機械可読な契約からコードを生成する方式は区別する必要がある。さらに「仕様を検証する」という説明も、文書形式の検査、文書間の論理的レビュー、実行時の契約検査、モデルの性質の検査で意味が異なる。

**4. 優先して詳しく見る8件**

**GitHub Spec Kit：機能仕様から実装への基本形**

プロジェクトの原則を定め、機能仕様、技術計画、タスク、実装へ接続するツールキット。spec、plan、tasksを分け、仕様と実装の照合もワークフローに含める。既存プロジェクトも対象であり、「新規開発専用」と限定するのは適切ではない。[^1][^64]

仕様テンプレートには優先順位付きユーザーストーリー、独立して試験できる単位、受入シナリオ、境界ケース、要求ID、主要エンティティ、測定可能な成功条件などがある。planは単なる日程表ではなく技術計画を指す。[^59]

テンプレートへの示唆は、機能の説明だけでなく「なぜ優先するか」「どう単独で確認するか」「何をもって成功とするか」を一組にすること。機能仕様の参考として有力だが、事業全体の利害調整や運用の全要件が自動で網羅されると考えるべきではない。

**OpenSpec：現行仕様と変更差分**

現行の仕様と、進行中の変更を分ける。変更側には提案、設計、タスク、追加・変更・削除する要求が置かれ、完了後に差分を現行仕様へ統合する。固定的な段階制より、成果物を更新しながら進める考え方に重点がある。[^2]

学べるのは変更管理の単位である。「現在どう動くべきか」と「今回何を変えるか」を別々に説明できるため、既存システムの改修を扱うテンプレートに向く。採用する場合は、仕様更新を完了条件に含め、変更履歴だけが残って現行仕様が古くなる状態を防ぐ必要がある。

**Kiro：要件・設計・タスクを製品内で扱う**

中心成果物はrequirements.mdまたはbugfix.md、design.md、tasks.md。機能追加では要件先行・設計先行を選べ、不具合仕様では現在の問題、期待する挙動、維持すべき挙動を扱う。IDE・CLI・Webの機能は同一ではなく、正しさのプロパティベーステスト支援などには提供面の差がある。[^3]

Feature SpecsはEARSを使って要求を構造化する。条件・イベントと期待動作を分ける記述は、曖昧な「適切に処理する」を具体化する参考になる。ただし構文を整えるだけで要求の完全性が保証されるわけではない。[^60]

追加候補として特に有用なのは、不具合修正の仕様である。正常系の期待だけでなく「変更してはいけない範囲」を明示すると、修正が新たな不具合を招かないか確認しやすい。

**cc-sdd：既存コードと責務境界**

Kiro型の仕様ワークフローを複数のコーディングエージェントで利用するための別プロジェクトで、日本語資料もある。Kiroそのものや公式拡張と同一視しない。要求・設計・タスクに加えて、調査、既存実装とのギャップ、設計検証を扱う。[^63]

現在のガイドでは、所有する責務、所有しない責務、許可された依存、下流の再検証条件を重視する。探索で候補を調べ、設計で境界を確定し、タスクや検証へ引き継ぐ。[^4]

参考になるのは、既存コード調査を単なるメモではなく、設計上の根拠と変更影響に変えること。「どのモジュールで実装するか」に加え、「どこへ責務を追加しないか」「何を再テストするか」をテンプレートに持たせたい。

**BMad Method：事業要求から実装仕様への段階化**

brief、PRD、UX、アーキテクチャ、実装用SPEC、storiesなどを扱う。現行資料は、案件に必要な計画経路を選ぶ考え方であり、すべての作業で一律に全成果物を作る方式ではない。共有のPRDと、限定された実装単位のSPECを区別する。[^5]

参考にすべきなのは、文書数より意思決定の粒度である。事業・製品の合意、技術上の合意、実装作業への引継ぎは読者と目的が異なる。大きな要件定義書をそのまま実装指示として渡さず、必要な要求を実装用仕様へ落とすという考え方が役立つ。

**Spec Kitty：仕様から作業パッケージ・受入まで**

仕様・計画・work packagesを、レビュー、受入、マージまで追跡する。worktreeによる並行作業や進捗表示を含む。確認時のmainには4.xのRC系列であることが示されており、mainの説明と安定版の機能を同じものとして扱わない。[^6]

参考になるのは、タスクの完了と受入完了を分けること。担当、依存、レビュー状態、受入条件を明記した作業パッケージは、多人数・多エージェント開発への引継ぎに有用と考えられる。

**GSD：長い開発での文脈・進捗・再開**

本資料で扱うのはgsd-build/get-shit-done。PROJECT、REQUIREMENTS、ROADMAP、STATEと、フェーズごとの計画・実行結果・検証記録を分ける。類似名称の別系統と混同しない。[^7]

設計テンプレートより、長期作業で何を覚えておくかの参考になる。「今どこまで合意・検証されているか」「次に何をするか」「何が阻害しているか」を残す再開・引継ぎ文書は、要件が複数回の作業にまたがる場合に価値がある。

**Superpowers：仕様を実装時の規律につなぐ**

仕様・設計の対話、実装計画、テスト駆動、レビューなどを組み合わせるSkills群。包括的な要求管理製品というより、実装を進める際の行動を支える。[^8]

参考になるのは、作成した文書をどう使わせるかという手順である。テンプレートだけでなく、実装前に何を確認し、いつテストし、何を根拠に完了を報告するかを定める必要がある。要求内容への適合とコード品質は、別のレビュー観点として扱うのがよい。

**7. 周辺ツールをどう組み合わせるか**

API契約の分野では、TypeSpecやSmithyが人の編集するモデルを起点に複数成果物を生成し、OpenAPI Generatorは既存のOpenAPIからクライアントなどを生成する。AsyncAPI GeneratorはイベントAPIの仕様を扱う。生成される範囲は言語・テンプレート・emitterに依存し、業務ロジックをすべて生成できるという意味ではない。[^33][^34][^35][^36]

検証にも役割分担がある。Spectralは仕様文書のルール違反を検査し、BufはProtobufの互換性を検査する。SpecmaticやSchemathesisはAPI実装と契約の一致を調べる。Pactは利用側の期待から契約を作って提供側を検証するため、設計書を先に書く方式と完全に同じではない。[^42][^37][^38][^39][^40]

BDDでは、受入例を人が読める形で書くことと、それを実行可能なテストへ接続することが分かれる。CucumberのGherkinやGaugeのMarkdown系仕様には、それぞれ実装側の接続が必要となる。「Given／When／Thenが文書にある」だけではテスト実行にはならない。[^44][^46]

TLA+、Alloy、Dafnyは、自然言語の曖昧さをAIがレビューする方式とは異なる。状態や関係、事前・事後条件などを明示し、定めた仮定・範囲で性質を検査する。XStateは状態機械を設計・実行へ近づける手段であり、これらと同じ意味の証明ツールではない。[^49][^50][^51][^52]

要求管理では、StrictDoc、Doorstop、Sphinx-Needsのようなリポジトリ・文書基盤と、Jama、Polarion、DOORS Nextのような組織向け製品がある。仕様からAIに実装させる機能より、要求の識別、関係、変更、レビューを維持する役割が中心となる。[^53][^54][^55][^56][^57][^58]

分析上は、次の組合せが考えられる。ここでの「＋」は役割の組合せであり、標準で直接連携できることを示さない。

| 案件の課題 | 組合せの候補 | 接続時に決めること |
|---|---|---|
| 機能仕様からAI実装を始める | Spec KitまたはKiro型ワークフロー＋通常のテスト | 要求IDと実装・テストの対応 |
| 既存製品を継続改修する | OpenSpec＋契約・回帰テスト | 現行仕様への統合条件、変更しない挙動 |
| 外部連携の事故を防ぐ | 仕様作成支援＋OpenAPI等＋Specmatic／Schemathesis／Pact | 正本、期待値、互換性の基準 |
| 複雑な業務判定を共有する | 機能仕様＋Cucumber／FitNesse等 | 入力例、期待値、実行コードへの接続 |
| 状態・並行処理の設計リスクを下げる | 設計書＋TLA+／Alloy、用途によりXState | モデルの仮定、検査範囲、実装との対応 |
| 多数の要求の証跡を残す | 仕様作成支援＋要求管理ツール | ID体系、レビュー、変更時のリンク更新 |

**8. create-requirements-docsへの適用候補**

対象スキルのassetsには、業務・対象者・関係者・スコープ・業務フロー・関連システム・機能・データ・非機能・受入と追跡の要件テンプレートがある。設計側にも基本設計、詳細設計、モジュール、データ、ADRがあり、開発計画も存在する。このため、事業要件や設計の大枠を一から置き換える必要性は低い。

以下は既存ファイルの構成から見た拡充候補であり、本文中に関連記載がまったくないと断定するものではない。独立した使い回し可能なテンプレートにする価値を評価した。新たなディレクトリ構造への再編は前提にしない。

| 優先度 | 拡充候補 | 最低限持たせたい内容 | 主な参考 |
|---|---|---|---|
| 高 | 機能・ユースケース単位の仕様 | 要求ID、目的、優先度、事前条件、正常・代替・例外、受入例、成功条件 | Spec Kit、Kiro |
| 高 | 仕様変更提案・差分 | 背景、現行と変更後、追加・変更・削除、互換性、影響、仕様更新条件 | OpenSpec |
| 高 | 不具合修正仕様 | 再現条件、実際と期待、維持する挙動、原因仮説、修正範囲、回帰確認 | Kiro |
| 高 | 既存実装との差分分析 | 調査対象、利用可能な既存機能、不足、制約、変更候補、根拠、未確認点 | cc-sdd、Shotgun |
| 高 | 要求適合・受入の検証報告 | 要求ID、確認方法、環境、結果、証跡、未達事項、承認者 | Spec Kitty、GSD、契約テスト群 |
| 中 | 責務境界と依存契約 | 所有／非所有、入出力、許可依存、不変条件、変更時の再検証対象 | cc-sdd、NodeSpec |
| 中 | 業務ルール・判断表 | 条件組合せ、優先順位、期待結果、例外、競合時の扱い | FitNesse、BDD群 |
| 中 | 状態遷移仕様 | 状態、イベント、ガード、アクション、禁止遷移、タイムアウト | XState、TLA+、Alloy |
| 中 | API・イベント契約の付属仕様 | スキーマ、互換性、エラー、冪等性、順序、再送、モック・テストとの接続 | TypeSpec、AsyncAPI、Buf、Specmatic |
| 中 | 実装作業パッケージ | 対応要求、前提、依存、変更範囲、非対象、完了条件、レビュー | Spec Kitty、Spec Kit |
| 中 | 調査・設計根拠 | 問い、比較案、評価軸、調査結果、採用理由、未確定事項 | cc-sdd、BMad |
| 低～中 | 作業再開・引継ぎ | 現状、合意済み事項、検証済み範囲、残件、阻害要因、次の作業 | GSD、APM |

優先度は、現在の要件・設計テンプレートを補うという目的に限定した推奨である。一般的な重要度ではない。例えば非機能、認証認可、セキュリティ、移行は重要だが、すでに対応するファイルがあるため、本調査から直ちに新規ファイルを重ねる候補とはしなかった。

最初の拡充単位としては、上位5件が扱いやすい。機能仕様で実装の入力を整え、変更・不具合仕様で改修を扱い、ギャップ分析で既存資産につなぎ、検証報告で完了根拠を残す。この一巡を作ると、文書の章数だけを増やさず、開発中の判断と確認を支援できる。

**9. テンプレートに共通して持たせる情報**

推奨する共通項目は、識別子、対象範囲、状態、根拠、未確定事項、関連要求、検証方法、変更履歴である。ただし、すべてをすべての文書へ重複記載するのではなく、正本への参照を使う。

特に「状態」は、草案、レビュー済み、承認済み、実装済み、検証済みを区別したい。文章が完成したこと、実装が存在すること、要求を満たした証拠があることは別である。同様に、要求・設計判断・実装タスクの識別子も役割を分けると追跡しやすい。

「成功条件」と「受入条件」も用途を分ける。事業上の成果と、特定の振る舞いの合否は一致しないことがある。利用率向上という成功条件だけでは、入力検証の正しさを判定できない。一方、すべてのテストが通っても製品価値が達成されたとは限らない。

仕様の機械化は段階的に進めるのがよい。まずIDや必須項目の静的確認、次に要求と設計・テストのリンク確認、さらにAPI契約や受入例の実行へ進む。最初からすべてを専用言語へ変換すると、書き手・読み手の負担が価値を上回る場合がある。

**10. 比較試験を行う場合の評価計画**

製品選定まで進める場合、同じ題材で少数候補を比較する。新規機能1件、既存機能の互換性を保つ変更1件、不具合修正1件を用意すると、仕様作成だけに偏りにくい。案件規模、使用モデル、入力資料、許可する実行操作をそろえ、実行時のツール版とテンプレート版を記録する。

| 観点 | 確認すること |
|---|---|
| 要求の具体性 | 曖昧な表現、根拠のない仮定、例外条件が残らないか |
| 範囲の制御 | 非対象、変更しない挙動、責務境界が守られるか |
| 既存資産への適合 | 既存の構造・API・規約を調べて再利用するか |
| 追跡 | 要求から設計・タスク・検証へ辿れるか |
| 変更追随 | 途中の仕様変更が関連文書と実装へ反映されるか |
| 検証の実質 | 完了チェックだけでなく、再現可能な試験と証跡があるか |
| 可搬性 | 文書・履歴を別ツールや通常のGit運用へ持ち出せるか |
| 人の負担 | 修正量、質問への回答量、レビュー時間、運用手順の複雑さ |
| 利用条件 | モデルAPIへの送信、権限、ライセンス、必要な契約・費用 |

検証では意図的な矛盾も入力する。例えば、既存APIの互換性を保つ要求と、応答フィールドを削除する設計案を同時に与える。その矛盾を指摘するか、未決事項として止めるか、黙って実装するかを比較する。単に整った文書を生成できるかより、誤った実装を防げるかを評価したい。

同様に、受入条件の一部を未実装のまま残し、完了判定がそれを見抜けるか確認する。これらは推奨する試験方法であり、本調査で各ツールに対して実施した結果ではない。

**11. 総合判断**

仕様駆動開発ツールは、単一の標準テンプレートへ収束していない。一方、要求を具体化し、設計判断を分離し、作業へ落とし、検証で閉じるという共通の構造は比較できる。ツールごとの差が大きいのは、仕様の粒度、変更の扱い、検証の強さ、作業環境への依存である。

要件定義スキルを拡充する場合の推奨は、Spec Kitから機能仕様、OpenSpecから変更差分、Kiroから構造化要求と不変の挙動、cc-sddから既存実装・責務境界、BMadから文書の目的と粒度を取り入れること。それに検証報告と機械可読契約への参照を足す。各ツール固有のコマンドやファイル配置は、その後に必要なら対応させればよい。
