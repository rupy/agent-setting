# 要件定義・設計の標準と実務ガイド

## 1. 結論と対象範囲

要件定義・設計には複数の標準があるが、すべての案件に共通する唯一の文書フォーマットはない。要求の品質・プロセスを扱う規格、品質の分類モデル、設計記述の規格、実務ガイド、テンプレート、図の記法は役割が異なる。

テンプレート拡充には、**29148で要求の品質と情報項目、BABOKとIPAで業務・合意形成、Volereで要求の具体化、25010とIPA非機能要求グレードで品質観点、42010・arc42・C4で設計の説明**を補う組合せを推奨する。これは本資料の適用提案であり、各規格がこの組合せを必須としているわけではない。

確認日は2026年9月16日。以前から検討対象としていた10件について、公式公開ページの概要、目次、公開テンプレート、版・状態を確認した。購入が必要な規格全文や会員向け資料をすべて精読した調査ではない。条項ごとの適合性判定や、規格準拠の認証を示すものではない。

関連資料：[仕様駆動開発ツール調査](spec-driven-development-tools-2026-09-14.md)。同資料が「仕様を作り、実装・検証へつなぐ手段」を扱うのに対し、本資料は「何を記述・検討すべきかの根拠」を扱う。

## 3. 要件定義の標準・ガイド

### 3.1 ISO/IEC/IEEE 29148:2018

- **対象**: システム・ソフトウェアの要求エンジニアリング。ライフサイクル中の要求関連プロセスと、そこで作成する情報項目・内容を扱う。公開目次には事業・ミッション分析、ステークホルダ要求、システム要求、要求管理などがある。[1][2]
- **位置づけ**: 単なるSRSのひな形ではなく、要求を作成・確認・管理する活動と成果物の基礎。公開説明は良い要求の特性や属性も対象としている。[2]
- **拡充案**: 要求ID、出所、理由、優先度、検証方法、関連要求、状態を要求票に持たせる。これらは適用案であり、ここに列挙した欄すべてを規格の必須欄と断定するものではない。
- **版の注意**: ISOは2018年版をPublishedとし、2024年に確認済みと表示する一方、DISによる改訂を案内している。草案を発行済み最新版と混同せず、採用時に版を固定する。[1]

### 3.2 BABOK Guide

- **対象**: IIBAが提供するビジネスアナリシスの知識体系。六つの知識領域にわたる活動、成果物、技法を扱う。システムへの機能要求だけに対象を限定しない。[3]
- **位置づけ**: 一つの要件定義書の章立てを規定するものではない。IIBAは別途、基礎的実務をまとめた無料のThe Business Analysis Standardも案内しているため、両者を同一資料として扱わない。[3]
- **拡充案**: 課題・期待価値、関係者と意思決定者、ヒアリング記録、要求の競合と優先順位、変更の承認、導入後の評価を補う。要件の内容だけでなく「誰がどう合意したか」を残す用途に向く。
- **利用上の注意**: 公開紹介とBABOK本文・KnowledgeHubのアクセス範囲は異なる。正式な引用や再利用では対象資料と利用条件を確認する。[3]

### 3.3 Volere Requirements Specification Template

- **対象**: 事業目的、関係者、制約、業務と製品の範囲、データ、要求などを体系的に記述するテンプレート。公開抜粋と、解説・例を含む完全版を区別している。[4]
- **特徴**: 公開例は、目標を測定可能にすることや、業務全体と製品が担う範囲の区別を重視している。[4]
- **拡充案**: 要求の説明だけでなく、必要な理由、根拠、具体例、合否を判断する条件を一組にする。業務ルールや用語集を別の機能記述へ埋没させない。
- **利用上の注意**: 公式ページには用途・販売等に関する条件がある。公開されていることを理由に、スキルへ全文を転載・再配布できるとは扱わない。参考にする観点と、転載する文章・テンプレートを区別する。[4]

### 3.4 IPA ユーザのための要件定義ガイド 第2版

- **対象**: 業務側・ユーザ企業の主体的な関与を支える実務ガイド。2019年発行、第2版2刷は2021年公開。業務要求、要件定義の管理、成果物の作成・整合などを扱う。[5]
- **特徴**: 公開目次は、データの管理、機能とデータの整合、非機能、運用・移行・総合テストの要求も対象にしている。画面・機能の一覧だけで要件定義を終わらせない参考となる。[5]
- **拡充案**: 業務側の確認事項、一覧間の整合チェック、運用主体、移行制約、受入体制などを補う。国内の発注者・受注者間で利用する資料として優先度が高い。
- **現状の注意**: 公式ページはアーカイブで、販売終了・事業終了が明記されている。PDFの公開と、継続更新・問い合わせ対応の有無は別に考える。[5]

## 4. 非機能・品質要求

### 4.1 IPA 非機能要求グレード2018

- **対象**: 非機能要求を項目として整理し、段階的な要求水準についてユーザと開発者が確認するためのツール群。項目一覧、グレード表、樹系図、活用シート、利用ガイドが提供されている。[6]
- **特徴**: 品質観点を列挙するだけでなく、どの水準を選ぶかの対話に使う。モデルシステムの値は出発点であり、すべての案件へそのまま当てはめる推奨ではない。
- **拡充案**: 非機能要求ごとに選択水準、その理由、適用条件、測定方法、コスト・制約、合意者を記録する。応答時間なら数値だけでなく、負荷・データ量・測定区間を明示する。
- **注意**: 公開資料は2018を基準とするため、現在のクラウド構成や案件固有の脅威・運用条件は追加点検する。資料ごとの使用条件も公式ページに案内されている。[6]

### 4.2 ISO/IEC 25010:2023

- **対象**: ICT製品・ソフトウェア製品の品質モデル。2023年版は九つの品質特性とその下位特性を用い、品質要求・測定・評価の共通観点を提供する。[7]
- **位置づけ**: 要求の数値や合格水準を案件ごとに決める代わりにはならない。「何を品質として見るか」のモデルであり、すべてを単純に非機能要求と同義にするのも避けたい。
- **拡充案**: 品質観点と具体的要求・測定・受入を対応させる表を用意する。適用しない観点にも理由を残せば、意図的な除外と検討漏れを区別できる。
- **版の注意**: ISOは2011年版をWithdrawn、2023年版をPublishedとしている。旧版の分類表を2023年版として掲載しない。[7]

**使い分けの提案**: 25010を品質観点の点検、IPA非機能要求グレードを要求水準の合意に使い、案件固有の測定条件と受入試験へ接続する。両資料の分類を無理に一対一対応させる必要はない。

## 5. 設計記述・可視化

### 5.1 ISO/IEC/IEEE 42010:2022

- **対象**: ソフトウェア、システム、企業などのアーキテクチャ記述の構造と表現。設計対象のアーキテクチャ自体と、それを説明する記述を区別する。[8]
- **特徴**: 記述、ビューポイント、モデル種別などの概念と関係を扱う。一方、特定の設計手法、ツール、表記法、ファイル形式を指定しない。[8]
- **拡充案**: 「誰のどの関心に、どの設計説明で答えるか」の対応表を追加する。構成図だけでなく、運用、品質、制約、判断の根拠を必要な読者へ説明できるようにする。
- **版の注意**: 公式ページでは2022年版がPublished、2011年版はWithdrawn。ISO規格への適合を主張する場合は、採用する版の本文を使った別途の確認が必要となる。[8]

### 5.2 arc42

- **対象**: ソフトウェアアーキテクチャを説明するための文書テンプレート。導入・目標、制約、コンテキスト、解決方針、構造、実行時、配置、横断的概念、判断、品質、リスク、用語を扱う。[9]
- **位置づけ**: ISO規格ではなく、設計文書を書く際の具体的な枠組み。章名をそのまま移植するより、既存の設計書が説明していない観点を補う用途に向く。
- **拡充案**: 実行時シナリオ、配置構成、横断的な設計方針、品質シナリオ、技術的リスクを優先的に点検する。ADRが既にある場合、同じ判断を複数箇所へ重複記載せず参照する。

### 5.3 C4 model

- **対象**: システムコンテキスト、コンテナ、コンポーネント、コードという抽象度で構造を説明する可視化モデル。補助的な動的図や配置図などもある。[10]
- **位置づけ**: 完全な設計書テンプレートや要求管理方式ではない。公式は表記法・ツールに依存しないモデルとして説明している。[10]
- **拡充案**: 図ごとに対象、読者、抽象度、境界、関係の意味を明記する。同じ図でシステム全体と個別クラスを混在させない。
- **注意**: すべての案件ですべての階層を作ることを目的にしない。また、C4のコンテナという抽象概念をDocker等の実行コンテナだけに限定して解釈しない。[10]

### 5.4 IEEE 1016-2009

- **対象**: Software Design Descriptionの内容・構成と設計情報の伝達を扱う規格。高水準・詳細設計の両方や、既存実装から設計記述を復元する場面にも適用範囲を持つ。[11]
- **現状**: IEEE公式はInactive-Reservedと表示し、2020年3月5日の非アクティブ化を記録している。現在も有効な最新規格として紹介しない。[11]
- **拡充案**: 設計の記録と説明の歴史的参考にはなるが、今回のテンプレート拡充では42010とarc42を先に検討する。既存契約で1016が指定されている場合は、その契約と指定版を別に確認する。
- **用語の注意**: ここでのSDDはSoftware Design Descriptionであり、Spec-Driven Developmentの略称とは別である。[11]

## 6. テンプレート拡充への適用案

以下は標準の要求事項そのものではなく、既存の要件・基本設計・詳細設計テンプレートを維持して拡充するための提案である。関連する記述が既存本文に一切ないという断定ではない。

| 拡充する情報・テンプレート | 優先する参照先 | 追加する判断・証拠 |
|---|---|---|
| 要求票・機能仕様 | 29148、Volere | 出所、理由、条件、合否、関連要求 |
| 業務要求の合意記録 | BABOK、IPA要件定義ガイド | 期待価値、意思決定者、競合、優先順位 |
| 品質要求の測定・受入表 | 25010、IPA非機能要求グレード | 品質観点、目標水準、測定条件、合意根拠 |
| アーキテクチャの説明対象表 | 42010 | 読者の関心と対応する設計説明 |
| 実行時・配置・横断設計 | arc42、C4 | シナリオ、配置、境界、関係、共通方針 |
| 運用・移行・受入の要求 | IPA要件定義ガイド | 責任者、切替・回復条件、確認方法 |
| 設計判断・リスク記録 | arc42 | 比較案、採否理由、残るリスク |

スキルに取り込む際は、参照規格の番号・版、参考にした範囲、独自に追加した項目を区別して残す。「参考にした」「対応関係を整理した」「規格の全要求に適合した」は異なる主張である。

この段階では既存フォルダの再編や規格本文の転載を行わず、不足項目の確認と独自テンプレートの設計に利用する。分野固有の安全・セキュリティ・アクセシビリティ規格、API記述仕様、業界・調達固有の標準は、本資料の10件とは別の追加調査対象とする。
