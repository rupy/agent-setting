# 判断に役立つ指示を設計する

AIに何を任せ、何を明記するかを整理する。規則を増やすことより、依頼の意図に沿う判断ができる指示を目指す。

- **対象**: SKILL.mdやAI向け指示文書の内容設計。既存の作成支援スキルや文章作成スキルと併用できる。
- **役割**: 規則の必要性・適用範囲・配置を判断する。ファイル形式や配置は、対象環境とリポジトリの規約に従う。

## 作業の進め方

1. **依頼と対象を特定する**: 新規作成・改訂・レビューの区分、解決したい問題、利用場面、変更できる範囲を把握する。
2. **根拠を確認する**: 現行文書、関連する指示、利用できる会話・修正履歴を読み、採用済みの方針と未確定の提案を区別する。[修正履歴からの抽出](#修正履歴からの抽出)を参照する。
3. **規則の採否を判断する**: 既存で対応・追加・統合・条件付き・対象外など、必要な扱いを選ぶ。[規則の採否](#規則の採否)と[具体性と適用範囲](#具体性と適用範囲)を参照する。
4. **指示を構成する**: 共通ルール、作業手順、条件付きの説明を整理する。[手順とルールの配置](#手順とルールの配置)を参照する。
5. **具体例で確認する**: 想定する依頼に当てはめ、必要な判断ができるか、不要な制約が生じないかを確認する。[確認と結果の提示](#確認と結果の提示)を参照する。

各段階は必要に応じて行き来する。質問だけの依頼では編集せず、対話的な検討を求められた場合は、指定された単位で案を示して合意済みの内容だけ反映する。通常の作成・改訂依頼に、項目ごとの承認を一律に要求しない。

## 修正履歴からの抽出

- **発言と解釈を分ける**: ユーザーが述べた修正理由、実際の変更、その理由から推定した一般原則を区別する。参照できない履歴や、文脈のない「はい」から採用内容を断定しない。
- **個別修正と再利用する規則を分ける**: 一つの文書で有効だった修正でも、別の場面に適用する必要性を確認する。
- **現行の規則と照合する**: 表現が違っても同じ判断を支援しているなら、未反映と決めつけない。意図的な削除や後から変更された方針を、追加漏れとして復活させない。

**例（修正理由から候補を示す場合）**:

> **確認できた意図**: 比較表の規則を全文章に適用しないため、対象を明記した。
>
> **一般化の候補**: 適用範囲が誤解される指示には、対象や条件を添える。

## 規則の採否

- **判断を変える規則を残す**: 明記しないと起きる誤解や、守るべき制約を説明できるか確認する。一般的な知識や、効果のない言い換えを規則として積み増さない。
- **AIが判断できる細部は任せる**: 成果の条件と判断基準を示し、支障のない実装・表現の選択肢を残す。ただし、依頼で指定された形式や、誤ると影響が大きい制約を「細かい」という理由で省かない。
- **同じ判断を支える規則は統合する**: 既存の規則で不足する条件だけを補う。項目数を減らすために独立した論点までまとめない。

**例（根拠のない細部の規定を見直す場合）**:

修正前：

> 各説明は必ず3項目の箇条書きにする。

修正後：

> 独立した確認事項は箇条書きにし、項目数は必要な情報に応じて決める。

指定テンプレートが3項目を要求する場合は、その制約を残す。

## 具体性と適用範囲

- **個別の対処を一律の規則にしない**: どの条件で役立った修正なのかを確認し、同じ判断が必要な範囲に限定する。
- **必須条件と選択肢を区別する**: 守る必要がある条件は明確にし、複数の方法が有効なら判断基準を示す。例の手段や数値を必須条件に変えない。
- **実行や確認ができる指示にする**: 「適切にする」だけで済ませず、何を見て判断するかを補う。手順の細部まで固定する必要はない。

**例（有効だった方法を固定しない場合）**:

修正前：

> 情報の関係は必ずMermaidで示す。

修正後：

> 図が理解を助ける場合は、掲載先で表示でき、関係を読み取れる形式を選ぶ。例えばMermaidを使える環境では、分岐をフローチャートで示せる。

## 手順とルールの配置

- **作業の順序と判断基準を分ける**: 手順は何から着手するかを示し、ルールは内容別に探せるようにする。同じ規則を複数工程で使う場合は、各手順から参照する。
- **意味のまとまりで分割・統合する**: 一緒に理解する内容はまとめ、独立した判断は分ける。目的に必要な判断の漏れと、分類の重なりを確認する。
- **共通ルールを一か所に置く**: 個別の対象には固有の条件を記載する。分けて読むために必要な短い再掲は残してよい。
- **詳細を必要なときに参照できるようにする**: 長い例や特定場面だけの説明は、分離した方が使いやすい場合に参照ファイルへ移す。短いスキルを形式だけで分割しない。

**例（共通ルールを参照する構成）**:

```text
作業手順
  作成：用語の統一ルールを適用する
  レビュー：同じルールで表記の不一致を確認する

内容別のルール
  用語の統一：同じ概念には同じ呼び方を使う
```

## 確認と結果の提示

- **適用する場面と境界を確認する**: 通常の依頼だけでなく、指定書式がある場合などにも当てはめ、意図した判断が保たれるか見る。小さな修正なら関連する例の点検に絞る。
- **形式と動作の確認を区別する**: メタデータや参照リンクの検査だけで、実際の応答品質まで確認できたとはしない。試行した範囲と残る不確実性を示す。
- **依頼に合う結果を示す**: 作成・改訂では完成した指示と主な変更理由を、レビューでは問題のある規則・判断への影響・修正案を示す。変更不要なら、その判断も明示する。

**例（規則の追加を見送るレビュー）**:

> **図表の用語統一**: 既存の「同じ概念には同じ呼び方を使う」で扱えます。図表専用の規則は追加不要です。
