## 文書メタデータ

各文書の先頭には原則として次を記載する。

```yaml
---
title: 文書名
status: draft
owner: 未定
reviewers: []
last_updated: YYYY-MM-DD
---
```

`status` は `draft`、`in-review`、`approved`、`superseded` のいずれかとする。日付を推測で入力せず、作業時の実日付または既存文書の規則に従う。

## 要件ID

| 種別 | プレフィックス | 例 |
|---|---|---|
| ビジネス目的 | `BO` | `BO-001` |
| ペルソナ | `PER` | `PER-001` |
| 業務フロー | `BP` | `BP-001` |
| 業務ルール | `BR` | `BR-001` |
| 機能要件 | `FR` | `FR-001` |
| データ要件 | `DR` | `DR-001` |
| システム連携要件 | `IF` | `IF-001` |
| 非機能要件 | `NFR` | `NFR-001` |
| 受入条件 | `AC` | `AC-001` |
| 仮定 | `ASM` | `ASM-001` |
| 制約 | `CON` | `CON-001` |
| 決定 | `DEC` | `DEC-001` |
| 未確定事項 | `ISSUE` | `ISSUE-001` |

IDは一度公開したら別の意味へ再利用しない。削除した要件のIDを詰め直す必要はない。

## 個別要件の属性

機能要件では、必要な属性だけを次から選ぶ。

```markdown
### FR-001 要件名

- 概要:
- 根拠:
- 対象利用者:
- 事前条件:
- トリガー:
- 入力:
- 基本処理:
- 出力:
- 事後条件:
- 例外:
- 権限制御:
- 優先度:
- 上位要求:
- 受入条件:
```

非機能要件では、対象、条件、目標値、許容上限、測定方法、優先度を優先する。根拠や測定環境が重要なら追加する。

## 優先順位

MoSCoWを用いる場合は次の意味に統一する。

- `Must`: リリース成立に不可欠。未達なら原則リリースしない。
- `Should`: 重要だが、合意した代替策があれば延期できる。
- `Could`: 余力があれば実現する。
- `Won't`: 対象範囲の検討対象だが、今回のリリースでは実現しない。

すべてをMustにしない。優先度を決定できない場合は、仮の優先度を付けず未確定事項にする。

## 文章表現

- 主語と対象を明確にし、「システムは〜できること」のように判定可能な文にする。
- 一文に複数の独立した要求を含めない。
- 代名詞や「など」を多用せず、対象を列挙または定義する。
- 「原則」「必要に応じて」「可能な限り」を使う場合は例外条件または判断者を記載する。
- 数値には単位、負荷条件、測定区間、パーセンタイルなど必要な測定条件を付ける。
- 法令・規格への適合は、対象名称、版、適用範囲、確認主体を明らかにする。

## 要件と設計の境界

業務上または外部制約上必要な技術指定は要件として記載できる。単なる実装案は設計へ分離する。

```text
要件: 利用者は会社の既存アカウントで認証できること。
制約: 既存認証基盤のOpenID Connectを使用すること。
設計: 認証処理を特定のライブラリの特定クラスで実装する。
```

## トレーサビリティ

基本の追跡方向は次とする。

```text
BO / BP → FR / DR / IF / NFR → AC
```

すべての要件を無理に一対一対応させない。複数の上位要求を持つ場合や、一つの受入条件で複数要件を検証する場合は、表で明示する。

## 品質チェック

各要件について次を確認する。

- 必要性: 上位の目的または根拠があるか
- 明確性: 読み手によって解釈が分かれないか
- 原子性: 独立した複数要求を含んでいないか
- 一貫性: 他の要件や用語と矛盾しないか
- 実現可能性: 制約内で実現できる見込みがあるか
- 検証可能性: 合否を客観的に判断できるか
- 追跡可能性: 上位要求と受入条件をたどれるか
- 必要十分性: 過剰な実装方法を固定していないか
