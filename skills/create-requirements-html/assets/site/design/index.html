モジュール詳細設計 責務、公開API、依存関係、内部構成、品質 条件付き draft 未定

条件付き文書の作成条件は次のとおり。

  • 外部システム連携設計: 外部システムまたは外部サービスとの連携がある場合。
  • 画面設計: 複数画面、画面遷移、複雑な入力・状態表示がある場合。
  • 共通UI詳細設計: 複数画面へ共通する入力、エラー表示、端末別動作、アクセシビリティの実装仕様を定める場合。
  • データストア詳細設計: 複雑な制約、整合性、検索性能、履歴、スキーマ変更を実装前に合意する必要がある場合。対象データストアごとに作成する。
  • モジュール詳細設計: 複数箇所で利用する、公開APIの互換性が必要、状態・並行処理が複雑、または障害影響が大きいモジュールの場合。対象モジュールごとに作成する。
  • セキュリティ設計: 個人情報・機密情報、外部公開、複雑な権限制御、固有の脅威がある場合。
  • 移行設計: 既存データ、利用者、設定、業務を新システムへ移す場合。
  • API設計: システムが画面、アプリ、他システムなどのクライアントへAPIを提供する場合。
  • 認証・認可設計: 利用者またはサービスを認証する場合、もしくは主体によって利用できる機能・情報を制御する場合。
  • 設計判断記録: 複数案の比較や、後から理由を再確認する必要がある重要な判断を行う場合。

設計原則

全設計で一貫して守る責務分離、依存方向、品質、変更容易性の方針を書く。

主要な設計判断

要件上の決定は requirements/appendices/decisions.md、実現方法の判断は decisions/ のADRを正本として参照する。

更新・レビュー方法

文書責任者、レビュー対象者、承認、要件変更時の更新方法を記載する。

条件付き文書は、対象となる外部連携・画面・共通UI仕様・複雑なデータ設計・難しいモジュール・セキュリティリスク・移行作業が存在する場合に作成する。重要な技術判断は decisions/ のADRへ記録する。

設計原則

  • 要件と制約を参照し、根拠のない構成を固定しない。
  • 外部連携の失敗が申請データを失わせない構成にする。
  • 重要な技術選択は比較した案と理由を決定記録へ残す。

主要な設計判断

  • DEC-001: 初回リリースの会計連携にはCSVを使用する。
  • DEC-002: Webアプリケーションとして提供する。

更新・レビュー方法

設計責任者が変更し、影響する要件IDと決定IDを更新する。要件または制約に影響する変更は要件責任者もレビューする。
