# HTML要件定義・設計資料の作成

人が読み、比較し、判断できるHTMLを成果物とする。Markdown版スキルの導入や中間Markdownの生成を前提にしない。既存のMarkdown資料は入力として利用できるが、依頼なしに変更・削除しない。

## 作業手順

1. 対象リポジトリの指示、既存成果物、要求、利用者、制約とGit差分を確認する。相談だけならファイルを変更しない。
2. `references/content-guide.md` を読み、今回必要な内容と文書境界を決める。分からない事実は仮定・未確定として示す。
3. 出力先の指定を優先する。指定がなければ `requirements-html/index.html`、設計は `design-html/index.html`、開発計画は `planning-html/index.html` を基準とし、既存ファイルを無断で置換しない。Markdownと併存する場合、HTMLが独立した正本か、指定時点の閲覧用派生物かを冒頭に明記する。両方を自動同期すると約束しない。
4. 対応する `assets/requirements.html`、`assets/design.html`、`assets/planning.html` を読み、共通表示とファイル内の記入例を利用する。必要な資料だけ作り、不要な節と目次項目は一緒に除く。
5. 例の固有名詞・数値・状態・判断を事実として転用しない。完成物から `data-reference-example` 付き要素と案内コメントを除き、空欄を確認済み情報または説明付きの未確定事項にする。本文全体をコードとして表示しない。
6. 要求・判断・受入をリンクで接続し、対象ファイルに検査スクリプトを実行する。ブラウザが使える場合は表示・キーボード操作・検索・印刷も確認する。構造検査だけならその限界を報告する。

## HTML表現

- 案件の内容に合わせて目次、比較表、組織のまとまり、カテゴリ別の要件カードを使う。表示のために要求や数値を追加しない。
- 本文を静的HTMLとして保持し、JavaScriptなしでも全内容・内部リンクを読めるようにする。検索は閲覧補助であり、採否・承認・保存操作にはしない。
- `lang`、文書タイトル、見出し階層、テーブルの見出し、入力ラベル、フォーカス表示を設定する。状態を色だけで伝えない。狭い画面では表・図の領域だけ横スクロールさせる。
- 図はSVGまたはHTML/CSSで埋め込み、文章や表でも同じ関係を説明する。Mermaid指定時はソースを残してSVGへ事前変換するか、利用が認められたローカルランタイムを添付する。ソースを置くだけで描画済みと扱わない。変換環境がない場合は未描画と明示する。
- 初期状態で重要な内容を隠さない。印刷時は検索による非表示を解除し、本文・図・出典を出力する。折りたたみは記入例など非必須の補足に限定する。
- CDN、外部フォント、分析タグ、ネットワークアクセスを既定で使わない。ローカルHTMLを開くだけで読める形にする。外部公開やアップロードはこのスキルの通常作業に含めない。
- 調査・入力の文章はHTMLとして実行せずエスケープする。ユーザー入力には `textContent` を使い、`innerHTML`、`eval`、イベント属性への文字列挿入を避ける。外部SVGやコードを無検査で埋め込まない。

## 更新と検証

要件IDはDOMの `id` と対応させ、移動・カテゴリ変更時にも維持する。見た目の変更で、未確定が承認済みに見えたり、例データが本番の要求に混ざったりしないよう確認する。要件の変更はスコープ、設計、候補の採否、受入、未確定事項への影響も確認する。

```sh
python3 scripts/check_html.py /path/to/output.html
```

このパスはスキルディレクトリ基準。複数ページの場合は全HTMLを渡す。検査はタグの対応、ID重複、ローカルリンク・アンカー、外部依存や例の残存を調べるもので、HTML標準への完全適合・描画・要件の正しさを保証しない。

ブラウザで確認できる場合は、幅390pxと1280px、検索の一致・不一致・解除、要件への直接リンク、JavaScript無効、印刷表示を試す。完成時は出力先、実行した検証、未検証事項だけを報告する。
