# HTML資料の内容と対応関係

このスキル単独で作成するための内容基準。項目数を満たすことより、案件の合意と検証に必要な情報を優先する。特定規格への完全準拠を称さない。

## 要件定義

| 領域 | 内容 | 表現 |
|---|---|---|
| 文書情報 | 目的、対象、状態、責任者、確認日、正本・派生物の区別 | 冒頭の説明・定義リスト |
| ビジネス | 背景、課題、価値、測定可能な成功指標 | 目的と根拠の表 |
| ターゲット・ペルソナ | 顧客と直接利用者の区別、典型像、課題、根拠・仮定 | 利用者とペルソナの対応図。架空の実在人物を作らない |
| ステークホルダー | 自社・顧客等の組織、部門・役割、受ける／与える影響 | 組織の枠内に役割を置く関係図。自社が指す組織を明記 |
| スコープ | 今回作るもの、対象外、制約 | 対象・対象外の比較 |
| 業務フロー | 開始・終了、実施者、受け渡し、分岐、例外、業務ルール | Before／Afterを同じ粒度で可視化。新規業務に架空のBeforeを作らない |
| 関連システム | 役割、情報の流れ、タイミング、障害時の業務対応 | 関係図と契約の表 |
| 機能 | 利用者の目的、理由、条件、入力、振る舞い、出力、例外、権限、優先度、受入 | 機能領域ごとのカテゴリ、FR単位のカード |
| データ | 意味、品質、所有、保持・削除、機密区分 | データ一覧。物理スキーマは設計へ |
| 非機能 | 品質、負荷条件、目標値、測定方法、運用、セキュリティ | 測定可能な条件の表 |
| 受入・追跡 | 上位目的・要求と試験、合否、証跡、未達事項 | ID間リンク。未実施を合格としない |
| 付録 | 用語、仮定・制約、判断と理由、未確定事項の担当・期限・次の行動 | 一元管理して参照 |

ターゲット・ペルソナは利用者理解が判断に影響する場合、Before／Afterは既存業務を変更する場合、外部連携は対象がある場合に作成する。責任分担表や承認体制は明示的に必要とされた場合だけ追加する。

## 競合調査と採否

競合調査が必要な場合は直接競合、間接競合、現状維持の代替手段を比較する。公式資料等の一次情報を確認し、出典URL、発行元、確認日、対象プラン・版・地域、実機確認の有無を記録する。未確認と非対応を混同せず、価格には課金単位・条件を添える。

候補にはCAND-ID、機能カテゴリ、調査根拠、利用者の課題・価値、今回の目的・範囲への適合、推奨理由、開発・運用負担、依存条件、追加検証を持たせる。採否は検討中／今回採用／将来検討／不採用とし、判断者・日付・根拠・反映状況を残す。競合が提供しているという理由だけで採用しない。

採用後は該当カテゴリのFR、スコープ、優先度、ACへ反映する。既存FRで満たせるなら重複追加しない。機能の根拠から候補へ戻れるようにし、未採用候補を確定要求に混ぜない。

## 設計

要件の「何を満たすか」と設計の「どう実現するか」を分ける。設計は依頼された範囲だけ作成する。

- **基本設計**: 全体構成、採用技術・用途・版方針、論理データ、インフラ・運用。対象がある場合に外部連携、画面、API、認証認可、セキュリティ、移行を追加する。
- **詳細設計**: アプリケーションの責務、プロジェクトディレクトリと依存方向。複雑なモジュール、データストア、共通UIの仕様は必要な対象だけ作る。コードから自明な全メソッドの一覧化はしない。
- **契約の境界**: 提供APIと外部サービス呼び出しを分ける。認証方式と認可条件、脅威と対策、画面仕様と内部実装を区別する。
- **判断**: 要求ID、制約、比較案、採否理由、影響、再検討条件をADRで追跡する。要件本文は複製せず参照する。
- **図**: 全体構成、データ関係、実行時、配置など読者の問いに必要な図を選ぶ。図の矢印と説明・仕様の意味を一致させる。

## 開発計画

機能領域とFR-IDを参照し、フェーズの目的・成果物・完了条件・依存・検証方法を定める。フェーズとリリースを同一視しない。日付・工数・担当を推測で埋めず、未確定と次の確認を残す。要件を計画内へ複製しない。

## IDと状態

BO（目的）、PER（ペルソナ）、BP（業務）、BR（業務ルール）、CAND（候補）、FR（機能）、DR（データ）、IF（連携）、NFR（品質）、AC（受入）、ASM（仮定）、CON（制約）、DEC（決定）、ISSUE（未確定）、ADR（設計判断）を識別に使う。既存案件にID規則があれば優先する。

基本の対応は `BO / BP → FR / DR / IF / NFR → AC`。競合由来は `出典 → CAND → 採否 → FR → AC` を補う。一つのIDは一つの検証可能な要求とし、カテゴリ変更で再採番しない。候補の採用状態、文書のレビュー状態、試験の合否を混同しない。

## 既存文書からHTMLを作る場合

元資料と確認時点を明示する。項目を省く場合は理由を示し、本文・表・図・注釈の意味と要件IDを維持する。HTML化を理由に要件を承認・採用済みに変えない。Markdownを残す場合、以後どちらを更新するか明記する。HTMLの表示を整える作業と、要件の実質的な改訂を分けて報告する。
